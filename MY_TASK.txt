# 🧠 YOUR ROLE — DEAL GOVERNANCE LAYER

This is the **most important engineering role in the team**.

Not because you write the most code, but because you define the thing that makes DealFlow360 **actually different from an Odoo Sales customization**.

Your responsibility is:

> **Build the deterministic Deal Governance Engine that continuously evaluates a deal, explains its risk, decides what governance is required, and orchestrates the next allowed action.**

The problem explicitly requires discount governance, automated approval routing, blended risk scoring, negotiation-triggered reapproval, fulfillment decisions and deal-health monitoring.

# 3. THE MOST IMPORTANT FUNCTION

Everything should eventually converge on something like:

```python
evaluate_deal(deal_id)
```

Conceptually:

```python
def evaluate_deal(deal_id):
    context = deal_service.get_context(deal_id)

    policy = policy_engine.resolve(context)

    risk = risk_engine.calculate(
        context=context,
        policy=policy,
    )

    approval = approval_engine.determine(
        context=context,
        risk=risk,
        policy=policy,
    )

    recommendations = recommendation_engine.generate(
        context=context,
        risk=risk,
    )

    fulfillment = fulfillment_engine.plan(
        context=context,
    )

    health = health_engine.calculate(
        context=context,
        risk=risk,
    )

    action = guardian.determine_next_action(
        risk=risk,
        approval=approval,
        fulfillment=fulfillment,
        health=health,
    )

    return decision
```

The exact implementation can differ, but **one orchestration entry point** is extremely valuable.

# 6. EFFECTIVE POLICY RESOLUTION

You need a deterministic precedence rule.

For example:

```text
Customer + Category specific policy
          ↓
Customer-tier policy
          ↓
Global policy
```

Or, if using the stricter rule:

```text
effective_limit =
MIN(customer_limit, category_limit)
```

The exact policy hierarchy is **our design choice**, because the problem statement gives the concepts and examples but does not specify one universal precedence algorithm.

Document the rule.

Do not hide it.

# 7. RISK ENGINE

This is your second major component.

The problem gives a "blended risk score" concept and explicitly explains that several smaller discount violations can accumulate into meaningful overall risk. 

## Start simple.

For each line:

```text
discount_excess =
max(
    0,
    actual_discount - allowed_discount
)
```

Then calculate contribution.

For example:

```text
line_risk =
discount_excess
× line_value_weight
```

Then:

```text
deal_risk =
sum(line_risk)
+ margin_risk
+ inventory_risk
+ approval_delay_risk
```

Again, the exact formula is **our design**, not a requirement given in the statement.

# 11. APPROVAL INVALIDATION RULE

Don't write:

```python
if discount_changed:
    approval = "pending"
```

That's too crude.

Instead:

```text
Material Change
      ↓
Re-evaluate
      ↓
Does previous approval still cover current state?
      ↓
YES → retain approval
NO  → invalidate approval
```

That means future versions can support different materiality rules.

# 15. FULFILLMENT PLANNER

The statement requires warehouse splitting and manual override. 

You receive:

```text

Required Qty
Warehouse stock

```

Then return:

```json
{
  "allocations": [
    {
      "warehouse_id": 1,
      "quantity": 9
    },
    {
      "warehouse_id": 2,
      "quantity": 6
    }
  ],
  "shipments": 2,
  "estimated_cost": 7200
}
```

### Start with a greedy algorithm.

Don't overthink it.

```text
1. Find warehouses with stock.
2. Rank them.
3. Allocate until demand is satisfied.
4. Remaining quantity = backorder.
5. Validate.
```

# 20. IMPORTANT: IDEMPOTENCY

This is an easy thing to overlook.

What happens if:

```text
DISCOUNT_CHANGED
```

fires twice?

We don't want:

```text
2 approval requests
3 audit records
4 notifications
```

Build idempotent event handling.

For example:

```text
event_id
+
processed_at
```

or a unique event key.

This is a **real backend engineering detail** that judges may appreciate if they ask about reliability.
